# Smart Campus Agent 전체 개발계획서 v0.1

**교수님 검토용 초안 | 2026년 9월 27일**  
**개발 대상:** 남서울대학교 컴퓨터소프트웨어학과 재학생  
**프로젝트 성격:** 4인 팀 캡스톤 디자인, 2026년 2학기부터 2027년 상반기까지 개발 예정

> **검토 요청:** 학과 단위로 범위를 제한한 서비스 방향, 다학기 학업 계획과 변경 시 재계획이라는 핵심 기능, 필요한 학사 자료의 확보 가능성을 우선 검토받고자 합니다. 본 문서의 학점·개설 시기·졸업 규정 등은 실제 자료로 확인하기 전까지 수치로 확정하지 않습니다.

## 1. 프로젝트 개요

### 1.1 문제와 대상

학생은 졸업요건, 교과목 이수 현황, 다음 학기 개설 과목, 진로 목표, 교내 프로그램을 서로 다른 곳에서 확인해야 한다. 과목을 이수하지 못하거나 수강 계획이 바뀌면 남은 학기 전체에 미치는 영향을 다시 계산해야 한다. Smart Campus Agent는 학생의 현재 상태와 목표를 입력받아 **근거를 확인할 수 있는 다학기 학업·진로 계획**을 제시하고, 계획 변경 시 가능한 대안을 다시 산출하는 서비스이다.

초기 사용자와 검증 범위는 남서울대학교 컴퓨터소프트웨어학과 재학생으로 제한한다. 다른 학과 확장은 초기 목표에 포함하지 않는다. 실제 학사 행정 시스템을 대체하거나 공식 졸업 판정을 내리는 서비스로 규정하지 않으며, 학생의 계획 수립을 돕는 시제품으로 개발한다.

### 1.2 서비스 결과물

- 개인별 이수 현황 및 남은 졸업요건 요약
- 선수과목·개설학기·수강 가능 여부를 고려한 다음 학기 후보 과목
- 남은 학기별 교과목과 진로 활동을 묶은 다학기 로드맵
- 수강 실패·학기 변경·목표 변경 시 영향과 대체 계획 비교
- 관련 교내 공지·프로그램의 출처 및 확인 시점이 포함된 안내

### 1.3 개발 원칙

학점 합계와 선수과목 같은 **검증 가능한 규칙은 구조화된 데이터와 결정적 계산**으로 처리한다. 검색 기반 AI는 공지 탐색, 내용 요약, 계획 설명과 질의응답에 사용하되 출처와 불확실성을 표시한다. 생성된 문장은 졸업요건 충족 여부를 임의로 판정하거나 검증되지 않은 과목 개설을 사실로 단정해서는 안 된다.

## 2. 핵심 목표 및 성공 기준

| 목표 | 시스템이 수행할 일 | 교수님과 함께 검토할 검증 방법 |
|---|---|---|
| 개인 상태 파악 | 이수 과목·성적 또는 이수 여부·현재 학기·잔여 학기를 입력 및 수정 | 준비된 학생 사례와 요건 계산 결과를 대조 |
| 졸업요건 분석 | 적용 학년도와 학과 규정에 따라 충족·미충족·확인 필요 항목 분리 | 학과 자료와 수작업 계산으로 교차 확인 |
| 수강 가능 과목 도출 | 선수과목, 재수강 여부, 예정 개설학기, 학점 한도 반영 | 경계 사례에서 제외 사유와 근거 점검 |
| 다학기 로드맵 | 필수 이수와 목표 분야를 함께 고려한 학기별 계획 생성 | 완주 가능 여부와 계획 설명을 사례별 검토 |
| 적응형 재계획 | 미이수·수강 취소·목표 변경 이후 기존안과 수정안 비교 | 변경 입력 전후 필수요건 누락 및 충돌 확인 |
| 근거 있는 정보 안내 | 교내 공지·프로그램을 검색하고 출처·확인 시점 표기 | 원문 일치 여부와 오래된 정보의 경고 확인 |

초기 평가의 최소 기준은 **규칙 위반 계획을 결과로 제시하지 않는 것**, 모든 미충족 요건에 사유가 표시되는 것, 입력 변경 후 관련 학기의 계획이 갱신되는 것이다. 성능 목표치와 평가 표본 수는 자료 확보와 교수님 검토 후 정한다.

## 3. 주요 사용자 시나리오

### 3.1 최초 학업 계획 수립

1. 학생이 적용 학년도, 현재 학기, 이수 내역, 졸업까지 예상 잔여 학기를 입력한다.
2. 시스템이 입력 누락과 적용 규정의 확인 필요 항목을 먼저 알려준다.
3. 졸업요건별 남은 항목을 계산하고, 다음 학기 수강 가능 과목 및 제외 사유를 보여준다.
4. 학생이 학기별 계획을 요청하면 필수과목·선수관계·학점 한도를 반영한 로드맵과 근거를 제시한다.
5. 필요한 자료가 없으면 해당 판단을 보류하고 학생이 확인할 항목을 명시한다.

### 3.2 진로 목표를 반영한 계획

학생이 예를 들어 AI 분야를 목표로 선택하면 관련 선택 과목과 교내 프로그램을 추천 후보에 반영한다. 추천마다 목표와의 관계, 수강 가능 여부, 출처를 구분해서 보여준다. 진로 추천은 졸업 필수요건 충족을 우회하지 않는다.

### 3.3 수강 실패 또는 계획 변경 후 재계획

학생이 과목 미이수, 수강 취소, 휴학·복학에 따른 잔여 학기 변화 또는 진로 목표 변경을 기록한다. 시스템은 기존 계획에서 영향을 받은 과목과 학기를 표시하고, 선수관계와 개설 시기 등을 다시 점검한다. 유효한 수정안을 제시할 수 없으면 어떤 제약이 충돌하는지 설명하고 학과 확인이 필요한 결정을 남긴다.

## 4. 기능 요구사항

| ID | 기능 | 초기 구현 범위와 사용자에게 보이는 결과 |
|---|---|---|
| F01 | 학업 정보 관리 | 적용 학년도·현재 학기·이수 과목·목표·잔여 학기 입력, 수정, 입력 오류 안내 |
| F02 | 졸업요건 분석 | 영역별 학점, 필수 교과목 등 충족 현황 및 판단 근거와 확인 필요 항목 표시 |
| F03 | 수강 가능 교과목 탐색 | 선수조건·기이수·개설 정보·학점 한도에 따라 후보와 제외 사유 제공 |
| F04 | 다학기 로드맵 | 남은 학기별 과목 배치와 목표 연계 활동 제안, 제약 검증 결과 표시 |
| F05 | Adaptive Re-planning | 학업 상태 또는 목표 변경 시 영향 분석, 기존안 대비 수정안 생성 |
| F06 | 개인화 추천 | 진로 목표에 부합하는 교과목·활동 후보 및 추천 이유 제공 |
| F07 | 교내 정보 검색 | 수집이 허용된 공지·프로그램 검색, 원문 링크·게시일·확인 시점 제시 |
| F08 | AI Assistant | 로드맵과 교내 정보에 대한 자연어 질의응답, 계산 결과 및 원문 근거 연결 |
| F09 | 대시보드 | 잔여 졸업요건, 이번 학기 할 일, 계획 변경 알림을 한 화면에 요약 |

**우선순위:** F01~F05를 핵심 시연 경로로 구현하고 F09로 결과를 제시한다. F06~F08은 신뢰 가능한 자료 확보와 핵심 기능 검증 결과에 따라 범위를 정한다. 각 기능의 세부 화면, API, 기술 스택은 팀원별 개발계획서를 취합해 후속 버전에서 확정한다.

## 5. 데이터 요구사항

| 데이터 묶음 | 필요한 항목 | 사용 목적 | 확보·검증할 사항 |
|---|---|---|---|
| 학과·졸업요건 | 적용 학년도, 졸업 총학점, 영역별 최소 학점, 필수 과목, 대체 인정 및 예외 규정 | F02, F04, F05 | 공식 학과·대학 자료의 연도별 버전과 해석 확인 |
| 교과목 | 코드, 명칭, 학점, 교과 구분, 선수과목, 개설 예정 학기, 폐지·변경 이력 | F03~F06 | 공식 교육과정 및 수업 공지와 대조; 미래 개설은 예정 정보로 구별 |
| 사용자 학업 정보 | 적용 규정, 학기, 이수·미이수 내역, 이수 학점, 계획 변경 내역 | F01~F05, F09 | 입력 최소화, 본인 수정 가능, 불필요한 개인정보 제외 |
| 사용자 목표 | 관심 분야, 우선순위, 희망 졸업 시기 또는 잔여 학기 | F04~F06 | 변경 이력과 계획 간 연계, 임의 추정 방지 |
| 교내 프로그램·공지 | 제목, 내용, 주관 부서, 지원 대상, 일정, 게시일, 원문 URL, 확인 시점 | F06~F08 | 수집·재사용 허용 범위, 최신성, 원문 연결 확인 |

학사 규정과 과목 관계는 **정형 데이터 및 규칙 버전**으로 관리한다. 공지와 프로그램 문서는 검색 가능한 원문 및 메타데이터로 관리한다. 검색 결과를 요약할 때는 어느 자료의 어느 시점 내용인지 연결한다. 데이터 수집 방식은 공개 자료·학과 제공 자료·검증용 수기 입력 중 허용되는 경로를 확인한 뒤 결정한다. 학사 시스템 연동 권한은 확보된 것으로 가정하지 않는다.

시연을 위해 실제 개인정보를 요구하지 않는 **가상 학생 사례**를 먼저 준비한다. 학번, 성적표 등 실제 개인 정보가 필요한 방식은 범위와 승인 절차를 별도 검토한다. 자료가 없거나 규정 해석이 불명확할 때에는 임의 값을 채우지 않고 `확인 필요` 상태를 유지한다.

## 6. 시스템 규칙 및 제약조건

### 6.1 반드시 지킬 학사 제약 Hard Constraints

| 규칙 | 계획 생성 및 재계획 시 확인할 내용 |
|---|---|
| 졸업 총학점 | 기이수와 계획 학점의 합이 적용 규정에 미달하지 않아야 함 |
| 영역별 요건 | 전공 등 해당 영역의 최소 이수 기준을 각각 확인해야 함 |
| 필수 교과목 | 필수 과목 또는 공식적으로 인정된 대체 관계를 누락하지 않아야 함 |
| 선수과목 | 후속 과목보다 앞선 학기에 선수요건을 충족해야 함 |
| 개설학기 | 확인된 개설 정보에 맞게 배치하고 미확정 미래 개설은 확정처럼 표기하지 않아야 함 |
| 학기별 최대 학점 | 적용 학년도 및 학생 상황에 따른 상한을 초과하지 않아야 함 |
| 남은 학기 | 학생이 설정한 잔여 학기 안에서 충족 가능성을 검사해야 함 |

**규칙 우선순위:** 공식 적용 규정과 하드 제약을 먼저 검사한다. 그 범위 안에서 진로 적합도, 학생 선호, 학기별 균형을 비교한다. 규정상 예외·대체·재수강 인정 방식이 확인되지 않았다면 자동으로 허용하지 않는다. 유효한 계획이 없으면 결과를 꾸며 제시하지 않고 충돌 요건과 추가 확인 사항을 보여준다.

### 6.2 재계획 규칙

1. 변경 사건과 변경 전 계획을 보존하고, 영향을 받는 후속 과목·학기를 찾는다.
2. 학생의 실제 이수 상태를 최신 입력에 맞춰 갱신한다.
3. 선수관계, 필수요건, 개설학기, 학점 한도 및 잔여 학기를 처음부터 재검증한다.
4. 가능한 경우 변경 폭과 졸업 시점에 미치는 영향을 명시한 대안을 제시한다.
5. 해결할 수 없는 충돌이나 자료 부족은 이유와 학과 확인 필요 항목을 표시한다.

### 6.3 AI 응답과 운영 제약

- AI의 설명은 규칙 엔진 계산과 확인된 자료를 근거로 생성한다. 계산값과 설명이 불일치하면 계산 결과를 기준으로 오류를 표시한다.
- 교내 공지 검색 답변에는 원문과 게시·확인 시점을 연결한다. 오래되었거나 원문을 찾을 수 없는 정보는 확정 안내로 사용하지 않는다.
- 학생에게 공식 졸업 심사나 실제 수강신청 성공을 보장하는 표현을 사용하지 않는다.
- 사용자 입력과 계획 이력은 최소한으로 저장하며, 인증·보관 기간·삭제 정책은 실제 서비스 범위가 정해진 뒤 설계한다.
- 실자료 접근 권한, 자료 갱신 주기, 팀의 구현 기간 및 인프라 비용에 따라 구현 깊이를 조정한다. 외부 시스템 자동 신청·학사 정보 수정은 초기 범위에서 제외한다.

### 6.4 다음 버전에서 확정할 항목

1. 교수님 또는 학과가 확인한 적용 학년도별 졸업요건과 규정 해석
2. 교과목·선수관계·개설 정보의 공식 출처와 갱신 방식
3. 실제로 확보 가능한 교내 공지와 프로그램의 수집 범위
4. 4인 팀 역할, 기능별 구현 담당, 학기별 일정과 시연 기준
